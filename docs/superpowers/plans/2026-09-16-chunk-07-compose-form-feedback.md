## F-001: A successful response erases text entered while the request was pending

- Severity: Important
- Finding: The message field remains editable during submission, but success unconditionally calls `setTextDraft("")`. A visitor can submit one message, start drafting the next while waiting, and lose all of that unsent text when the first request resolves. The pending test only checks a second button click; it does not edit the textarea. The success belongs to the submitted snapshot, not necessarily the draft currently displayed.
- Evidence: `docs/superpowers/plans/2026-09-16-chunk-07-compose-form.md:66` chooses editable fields during pending; `:1204` awaits the submitted snapshot, `:1206` clears the draft unconditionally, and `:1249` disables the textarea only for the external `disabled` prop. PRD §4 Compose behavior (`docs/PRD.md`) requires clearing only after confirmed success and protecting drafts. The React/jsdom probe recorded `sent[0].text = "first message"`, `draftBeforeResponse = "second, unsent draft"`, `draftAfterResponse = ""`.
- Recommendation: Specify a consistent policy in the design decision, component, and tests. Either disable editing during the request, or track draft revisions and clear only if the message still belongs to the submitted revision. If editing remains enabled, also define how late validation errors relate to the edited fields. Add a deferred-promise test that edits during pending and verifies the chosen behavior on success and failure.
- Decision: Accepted (2026-09-17; user: “approved”). Previously Pending.
- Implementation status: Implemented in plan. Previously Not started.
- Implementation evidence: `docs/superpowers/plans/2026-09-16-chunk-07-compose-form.md:66` chooses disabled editing during pending; `docs/superpowers/plans/2026-09-16-chunk-07-compose-form.md:992` adds deferred success/failure tests that attempt typing and repeated clicks; `docs/superpowers/plans/2026-09-16-chunk-07-compose-form.md:1250` guards submission and the component uses `disabled || pending` on both fields and the button. ## F-002: The room-panel callback does not type-check against the newer feed contract

- Severity: Important
- Finding: The handoff passes `(input) => feed.send(input)` directly to a callback requiring `Promise<void>`. The newer room-feed design returns `Promise<Message>` from both store and hook. Those promise types are not assignable, so following the two documents together fails type checking when chunk 9 mounts the form. Chunk 7's mock returns void and its standalone checks cannot expose the mismatch. This is drift between incomplete downstream designs, not an unavailable prerequisite for the form itself.
- Evidence: `docs/superpowers/plans/2026-09-16-chunk-07-compose-form.md:1159` fixes the callback type and `:1419` supplies the incompatible handoff. `docs/superpowers/specs/2026-09-16-room-feed-design.md:311` returns the posted message and `:332` declares `RoomFeed.send(): Promise<Message>`. The older chunk document still declares `Promise<void>` at `docs/superpowers/specs/2026-09-16-map-chat-implementation-chunks.md:584`. The contract probe reproduced TS2322.
- Recommendation: Preserve the chunk 7 contract and adapt at the panel boundary: `onSubmit={async (input) => { await feed.send(input); }}`. This discards the fulfilled value while preserving rejection. Add the newer feed design to the handoff references, explicitly reconcile its pending status, and require the actual chunk 9 wiring to type-check once that feature exists. If the feed contract is instead intentionally changed, update its owning design rather than silently assuming the older signature.
- Decision: Accepted (2026-09-17; user: “approved”). Previously Pending.
- Implementation status: Implemented in plan. Previously Not started.
- Implementation evidence: `docs/superpowers/plans/2026-09-16-chunk-07-compose-form.md:13` adds the newer feed contract; `docs/superpowers/plans/2026-09-16-chunk-07-compose-form.md:1478` uses the awaited void adapter, readiness gating, and known no-write error translation; `docs/superpowers/plans/2026-09-16-chunk-07-compose-form.md:1481` requires real boundary type/error tests. ## F-003: The creation handoff omits the first message required to seed the feed

- Severity: Important
- Finding: The new-room handoff says to dispatch `roomCreated`, referring to the map-shell action that carries only a room. It never tells the caller to retain the `message` returned by successful atomic creation and pass it to the new room's feed. The current selection/panel contracts have no complete path for that value. Following the handoff would open the room as an ordinary existing room and fetch initial history, rather than initialize the displayed first message and synchronization bookmark from the confirmed POST result. This is unfinished integration across chunks 6/9/10, not a reason for the compose component itself to own feed state.
- Evidence: `docs/superpowers/plans/2026-09-16-chunk-07-compose-form.md:1420`; `docs/superpowers/specs/2026-09-16-map-shell-design.md:238` defines `roomCreated` with only `room`. `docs/PRD.md:244`–`:248` requires a newly created room to initialize its bookmark from the returned first message. `docs/superpowers/specs/2026-09-16-room-feed-design.md:31` requires seeded opening without a history fetch; `:340` accepts `opts.seed` and `:351` says later seed changes are ignored. The actual chunk 4 `CreateRoomOutcome` in `/Users/calin/dev/other/wp-worktrees/chunk-04-rooms-api/src/lib/api/client.ts:36` already supplies the first message for the `created` branch.
- Recommendation: Make the handoff explicitly assign chunks 6/9/10 the task of carrying the created outcome's message through selection or equivalent parent state, into the room panel, and into `useRoomFeed(room.id, { seed: message })` on its first mount. Update those owning contracts when implemented. Keep the 409 path separate: transfer author/text as an unsent prefill and load the existing room normally. Require an integration/component test proving that creation displays the returned first message, seeds its cursor, and avoids an initial-history request, while conflict posts nothing automatically.
