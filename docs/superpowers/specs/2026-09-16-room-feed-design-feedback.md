## F-001: Hook lifecycle starts effects during render and lacks a safe mount contract

- Severity: Blocker
- Finding: The store starts HTTP/subscription effects in its constructor, but the hook constructs it during render and disposes it on unmount. Uncommitted renders have no cleanup owner. Under the ordinary effect-cleanup implementation, Strict Mode's cleanup/setup replay leaves the ref pointing at a permanently disposed store. The two-argument `useSyncExternalStore` also throws during server rendering; the shared-room entry path has no specified client-only boundary. These prescriptions must be reconciled before the store and hook can be planned soundly.
- Evidence: `docs/superpowers/specs/2026-09-16-room-feed-design.md:291`, `:314`, `:344`, `:349`, `:420`; `docs/superpowers/specs/2026-09-16-map-shell-design.md:55` and `:258`; installed Next docs `node_modules/next/dist/docs/01-app/01-getting-started/05-server-and-client-components.md:109` describe client-component prerendering, and `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/reactStrictMode.md:8` documents the App Router default. The probes above reproduced both failures. See React's [server snapshot contract](https://react.dev/reference/react/useSyncExternalStore#parameters) and [effect replay behavior](https://react.dev/reference/react/StrictMode#fixing-bugs-found-by-re-running-effects-in-development).
- Recommendation: Specify side-effect-free construction with committed lifecycle ownership of start/cleanup and fresh or safely restartable storage after cleanup replay. Define a stable server/hydration snapshot, or an explicit boundary that prevents server rendering of the feed. Include Strict Mode replay, unmount, room replacement, and direct shared-room rendering in acceptance coverage; require no transport work from abandoned/server renders.
- Decision: Accepted (2026-09-17; user: “approved”). Previously Pending.
- Implementation status: Implemented in spec. Previously Not started.
- Implementation evidence: `docs/superpowers/specs/2026-09-16-room-feed-design.md:339` specifies inert creation and explicit start; `docs/superpowers/specs/2026-09-16-room-feed-design.md:415` specifies the committed fresh-store lifecycle and server/hydration bridge; `docs/superpowers/specs/2026-09-16-room-feed-design.md:527` adds lifecycle acceptance coverage. ## F-002: Failure fallback retains the failed channel and bypasses close cleanup

- Severity: Important
- Finding: Both channel-failure transitions set `channel = 'none'` without emitting `unsubscribe`. The store still retains its handle, and the adapter suppresses callbacks/removes the channel only when that handle is unsubscribed. A later close also omits unsubscribe because reducer state says there is no channel. Errors/timeouts can therefore leave SDK rejoin work running alongside polling or after room closure. Later successful callbacks are ignored by the reducer while the underlying subscription can remain alive, contradicting the stated send-only resubscription policy.
- Evidence: `docs/superpowers/specs/2026-09-16-room-feed-design.md:188`, `:189`, `:234`, `:301`, `:383`; `docs/KNOWN_LIMITATIONS.md:55` explicitly couples failure fallback with previous-subscription cleanup. Installed `node_modules/.pnpm/@supabase+phoenix@0.4.5/node_modules/@supabase/phoenix/assets/js/phoenix/channel.js:46`, `:64`, `:72`, `:79` schedule rejoins on socket restoration, join errors, channel errors, and timeouts; `:238` resets the rejoin timer on leave. Supabase documents [channel removal](https://supabase.com/docs/reference/javascript/removechannel) as unsubscribe plus removal.
- Recommendation: Make failure terminal for that subscription attempt: invalidate its handlers, unsubscribe/remove its handle, then select polling. Define cleanup ownership even if state has already become `none`, including synchronous failure during adapter creation. Add failure→close and failure→late-callback cases, asserting that no old subscription or rejoin survives and only a subsequent send creates a new attempt.
- Decision: Accepted (2026-09-17; user: “approved”). Previously Pending.
- Implementation status: Implemented in spec. Previously Not started.
- Implementation evidence: `docs/superpowers/specs/2026-09-16-room-feed-design.md:184` and `docs/superpowers/specs/2026-09-16-room-feed-design.md:209` require cleanup on failure; `docs/superpowers/specs/2026-09-16-room-feed-design.md:357` specifies terminal tokens, synchronous-failure handle retention and unconditional disposal; `docs/superpowers/specs/2026-09-16-room-feed-design.md:481` specifies SDK cleanup; `docs/superpowers/specs/2026-09-16-room-feed-design.md:531` adds failure/late-callback coverage. Initial evidence: None yet. Product behavior remains unverified.

## F-003: Hiding during opening or subscription can leave realtime active in the background

- Severity: Important
- Finding: `hidden()` only dispatches `idle`, and `idle` is ignored unless already subscribed. If the visitor hides the tab while initial history is pending or the channel is subscribing, the eventual history/confirmation still starts realtime and its full idle timeout. Activity tracking only reacts to visibility changes, so attaching while the document is already hidden also misses inactivity. No later visibility event is guaranteed to correct the mode. This violates the retained requirement that hidden means inactive immediately.
- Evidence: `docs/superpowers/specs/2026-09-16-room-feed-design.md:27`, `:176`, `:186`, `:191`, `:192`, `:310`, `:394`; `docs/PRD.md:236` specifies immediate hidden-tab inactivity. The trace `historyLoaded → hidden/idle → subscribed` ignores the middle action and ends subscribed; `hidden/idle → historyLoaded → subscribed` does likewise during opening.
- Recommendation: Define how current visibility is retained or checked during opening and subscription confirmation, and how a pending attempt is cancelled/invalidated when hidden. Initialize tracking from the document's current visibility. Keep the chosen hidden-tab polling behavior; foreground refresh and suspension of polling need not be added. Test already-hidden attachment, hiding during initial fetch, hiding during initial/re-subscription, and a send response completing after the tab hides.
- Decision: Accepted (2026-09-17; user: “approved”). Previously Pending.
- Implementation status: Implemented in spec. Previously Not started.
- Implementation evidence: `docs/superpowers/specs/2026-09-16-room-feed-design.md:215` records hidden state and drops pending/live channels; `docs/superpowers/specs/2026-09-16-room-feed-design.md:423` initializes and tracks document visibility from chunk 9; `docs/superpowers/specs/2026-09-16-room-feed-design.md:447` and `docs/superpowers/specs/2026-09-16-room-feed-design.md:534` cover no foreground auto-resubscription and the opening/join/POST races. Initial evidence: None yet. Product behavior remains unverified.

## F-004: Failed subscription catch-up can leave an active realtime feed incomplete indefinitely

- Severity: Important
- Finding: Confirmation stops polling before catch-up succeeds. Any fetch failure then clears `newerWanted` and leaves the channel subscribed, with no polling timer. A failed catch-up therefore has no next poll tick; continued activity/sends can keep realtime alive indefinitely while messages from before confirmation remain absent. The same loss of the catch-up obligation occurs when confirmation queues it behind an older-page request that then fails. `loadNewer()` exists, but the specified UI exposes it for `backlog`, which can still be false after these failures. The error can be dismissed without recovering synchronization.
- Evidence: `docs/superpowers/specs/2026-09-16-room-feed-design.md:28`, `:166`, `:186`, `:223`, `:231`, `:233`; `docs/superpowers/specs/2026-09-16-map-shell-design.md:317`; `docs/PRD.md:249` requires confirmation catch-up and `:352` requires coverage of messages committed between history and confirmation.
- Recommendation: Choose an explicit recovery contract for failed or queued confirmation catch-up: for example, fall back to polling while retaining the bookmark, or expose a persistent unsynchronized state and a manual retry independent of `backlog`. Specify how failures of unrelated older fetches affect an owed catch-up and when a successful recovery clears the error. This need not introduce backoff or automatic write retries. Cover both failure sequences and prove a subsequent successful recovery retrieves the missing messages without moving the cursor on failure.
- Decision: Accepted (2026-09-17; user: “approved”). Previously Pending.
- Implementation status: Implemented in spec. Previously Not started.
- Implementation evidence: `docs/superpowers/specs/2026-09-16-room-feed-design.md:263` defines operation-specific recovery, retained cursor, delayed polling retry, queued catch-up after older failure, terminal 404, and matching-error clearing; `docs/superpowers/specs/2026-09-16-room-feed-design.md:537` adds recovery/backlog acceptance coverage. Initial evidence: None yet. Product behavior remains unverified.

## F-005: Sending before the feed opens can discard a confirmed message

- Severity: Important
- Finding: `send()` always posts, but `received` and `sent` are ignored while `status === 'opening'`. A send during initial loading can therefore resolve successfully without displaying its response. More seriously, an initial fetch failure leaves the feed opening with no transports; a subsequent successful send is ignored forever until reopening. The hook exposes no status/readiness flag, and after that initial error is dismissed its public fields no longer distinguish failed opening from a ready, idle feed. The panel contract does not state that composing must wait for successful history initialization.
- Evidence: `docs/superpowers/specs/2026-09-16-room-feed-design.md:221`, `:225`, `:231`, `:233`, `:311`, `:323`; `docs/PRD.md:56` requires posting through the room compose box and `:114` clears text after confirmed success; chunk 5's display handoff is `docs/superpowers/plans/2026-09-16-chunk-05-messages-api.md:112`.
- Recommendation: Decide whether posting is allowed before history initializes. If it is disabled, expose durable readiness through the hook, require the panel to use it, and define rejection without a POST at the store boundary. If it is allowed, retain successful POST messages across opening/history completion without using them to advance the synchronization bookmark. Test slow and failed initial history, error dismissal, and a successful send response arriving before history; preserve the visitor's draft whenever submission is blocked.
- Decision: Accepted (2026-09-17; user: “approved”). Previously Pending.
- Implementation status: Implemented in spec. Previously Not started.
- Implementation evidence: `docs/superpowers/specs/2026-09-16-room-feed-design.md:374` defines no-POST readiness rejection and pending-send settlement; `docs/superpowers/specs/2026-09-16-room-feed-design.md:437` defines panel disabling, durable failed-opening guidance and known-no-write form-error mapping; `docs/superpowers/specs/2026-09-16-room-feed-design.md:542` adds draft/readiness acceptance coverage. Initial evidence: None yet. Product behavior remains unverified.
